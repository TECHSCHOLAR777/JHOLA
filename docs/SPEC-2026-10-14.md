# Jhola: one grocery list, three apps, the cheapest real basket

Jhola is a working name. Rename it before submission if you want.

## What it is

Jhola is a web app for people who order groceries on Blinkit, Zepto and Swiggy Instamart. The user types one shopping list in plain words. TinyFish agents read live prices on all three apps, and Jhola works out the cheapest way to buy the whole list after delivery, small-cart and handling fees. Sometimes that means one app, sometimes a split across two or three. Jhola then fills the real carts on the user's logged-in accounts and stops at the payment page. The user approves the plan and pays with their own UPI.

## Who it is for

The first user is a parent who orders household groceries every week and does not compare three apps by hand. The person who sets it up (us) connects the three accounts once. After that the parent only uses the Jhola web app.

## What the user does

1. Setup, once per app. The user opens Jhola's setup page, picks an app, and logs in with their phone number and OTP inside a TinyFish browser session. Jhola saves the session to a TinyFish browser context profile. The user also confirms the delivery address once.
2. The user types a list such as "doodh 2 packet, atta 5kg, maggi 4, dhaniya". Hinglish, loose quantities and brand names all work.
3. Jhola shows three columns, one per app, with each app's TinyFish browser streaming live into the page. Prices fill in as the agents find them.
4. Jhola shows the plan. For example: "Blinkit + Zepto, Rs 1,240 including fees. Best single app is Zepto at Rs 1,358. You save Rs 118." Each line shows the chosen product, its pack size, its price per unit, and a flag if it is a substitute.
5. The user can swap a product, drop an item, or force a single app. The totals update immediately.
6. The user taps Approve. Agents fill each chosen cart and report back the cart total the app shows.
7. Jhola shows each cart's total next to the planned total and opens the payment step. The user pays in the app. Jhola never pays.

## What we build

### Web app (Next.js, TypeScript)

- Setup page: connect Blinkit, Zepto and Instamart, show which apps have a saved login and when it was saved.
- List page: a text box and an "item preferences" field per item (brand, size, "no substitutes").
- Live page: three panels with the embedded TinyFish `streaming_url` iframe for each app, plus a progress line from the run's `PROGRESS` events.
- Plan page: the basket table, the fee breakdown per app, the savings against the best single app, and the Approve button.
- Cart page: per-app cart totals from the fill runs, the payment handoff, and any errors.
- Watchlist page: products the user buys often, with price-drop alerts from Monitor.

### Backend (Next.js route handlers, TypeScript, `@tiny-fish/sdk`)

1. **List parser.** An LLM call turns free text into items: `{ name, quantity, unit, brand?, allowSubstitute }`. "doodh 2 packet" becomes milk, 2 x 500 ml, substitutes allowed.
2. **Price collector.** One Agent run per app, logged in through that app's profile, searches every item in the list and returns the top three matches per item through `output_schema`. Runs go out together and TinyFish queues anything over the account's concurrency limit.
3. **Product matcher.** Pure code plus one LLM call. It converts each candidate to a price per unit (Rs/kg, Rs/L, Rs/piece), checks pack size against the requested quantity, and ranks candidates by exact match, same brand in a different size, then substitute.
4. **Fee reader.** The cart-reading step of the Agent run reports the fees the app actually shows: delivery fee, small-cart fee and its threshold, handling fee, and any surge or rain fee. Nothing about fees is hardcoded, because fees change by location, time and order value.
5. **Basket optimiser.** Pure TypeScript with unit tests. For every app combination (three single apps, three pairs, one triple) it assigns each item to the cheapest available app in that combination, adds each app's fees for its subtotal, and keeps the lowest total. It then tries moving single items between apps to cross a small-cart threshold or remove an app entirely. With three apps there are only seven combinations, so the search is exhaustive and instant. Quality is a tie-breaker only: when two options are within Rs 5, the one with the higher app rating wins.
6. **Cart filler.** After approval, one Agent run per chosen app adds the planned products and quantities, opens the cart, and returns the cart line items and total. It stops before any payment button.
7. **Price watch.** A TinyFish Monitor per watched product page, scheduled daily with `CRON_TZ=Asia/Kolkata`, posts to a Jhola webhook when the page changes. Jhola parses the new price and shows an alert.
8. **Run store.** SQLite holds lists, plans, run ids, results and errors, so a page refresh or a dropped stream does not lose a run. After a drop the backend polls `GET /v1/runs/{id}`.

## How Jhola uses TinyFish

| TinyFish product | Endpoint | Job in Jhola |
| --- | --- | --- |
| Agent | `POST /v1/automation/run-sse` with `use_profile`, `profile_id`, `output_schema` | Logged-in search on each app, fee reading, cart filling up to the payment page |
| Browser context profiles | `POST /v1/profiles`, `/setup-session`, `/save` | One saved login per app, created with `proxy_country_code: "IN"` |
| Browser | `POST https://api.browser.tinyfish.ai` with an India proxy, driven by Playwright over `cdp_url` | Logged-out price scan at the user's pincode, fast and scripted. Also the fallback when an Agent search run fails. |
| Search | `GET https://api.search.tinyfish.ai` | Finds the public product page URL of each watched product on each app, for example `site:blinkit.com amul taaza 500ml` |
| Fetch | `POST https://api.fetch.tinyfish.ai` | Reads those public product pages to confirm name, pack size and the URL before a Monitor is created on them |
| Monitor | `POST /v1/monitors`, type `fetch` | Daily price watch on the user's regular products |

Each product does a job the others cannot do. Agent handles logged-in, judgement-heavy steps. Browser handles fast scripted scans where Playwright selectors are stable and an Agent step would cost more. Search and Fetch find and confirm public pages without a browser. Monitor runs on a schedule with no code of ours running.

## Getting past bot protection

TinyFish's anti-bot guide gives these settings, and Jhola uses all of them.

- Every Agent run sets `browser_profile: "stealth"` and runs on a profile created with `proxy_country_code: "IN"`. The guide says stealth and proxy work together because sites check fingerprint and IP at the same time. Runs on a profile use the profile's proxy, which is how Agent runs get an Indian IP. The per-run `proxy_config.country_code` list does not include IN.
- Browser API sessions use `proxy_config` with country `IN`, which the Browser API accepts.
- If the TinyFish India pool is blocked, the fallback is `proxy_config.type: "custom"` with our own Indian residential proxy URL.
- Logged-in sessions pass checks that block anonymous traffic, so the price and cart runs both use the saved profiles.
- Goals start at the app's home page and search from there, because deep links look robotic.
- Each run does one app and stops when done, which keeps time on each site short.
- Runs are staggered by a few seconds instead of fired at once.

TinyFish cannot solve CAPTCHAs. If one appears, the run returns `{ "error": "blocked" }`, Jhola marks that app unavailable for this list, and the plan uses the other apps.

## Goal writing rules we follow

These come from the TinyFish goal prompting guide.

- Use numbered steps for multi-step flows, and say what to remember between steps.
- List the exact fields to return and pass an `output_schema`. Include sample values in the goal so field names and types do not drift between runs.
- Describe elements the way they look ("the green ADD button under the price"), not by CSS selector.
- Give guardrails. Every search and cart goal says "Do not click Proceed to Pay, Place Order or any payment button."
- Give termination conditions: stop after the last item, stop if a login page appears, stop if an access-denied page appears.
- Give explicit fallbacks for out-of-stock items, items not found, and blocked pages.
- Keep each run well under the 10-minute run timeout.

Draft of the search goal (one run per app):

```
1. Wait for the page to fully load. Close any popup or banner.
2. Check the delivery address at the top of the page. Remember it as delivery_address.
3. For each item in this list, do steps 4 to 6:
   {{items}}
4. Click the search bar at the top, clear it, type the item name, and press Enter.
5. Wait for results to load.
6. Note the first 3 results that match the item: product name, pack size as shown,
   selling price, MRP if shown, and whether the ADD button is available.
7. Do not add anything to the cart. Do not click any payment button.

If an item has no results, return it with "found": false.
If a login page appears, stop and return { "error": "logged_out" }.
If an access denied page or CAPTCHA appears, stop and return { "error": "blocked" }.

Return JSON like this example:
{ "delivery_address": "Sector 7, Rohini", "items": [ { "query": "amul taaza milk 500ml",
  "found": true, "results": [ { "name": "Amul Taaza Toned Fresh Milk", "pack": "500 ml",
  "price": 28, "mrp": 28, "in_stock": true } ] } ] }
```

Draft of the cart goal (one run per chosen app):

```
1. Wait for the page to fully load. Close any popup or banner.
2. Open the cart. If it has any items, remove all of them and remember that you did.
3. For each product below, search for it, find the result whose name and pack size
   match exactly, and click ADD. Use the + button until the quantity matches.
   {{products}}
4. Open the cart. Wait for the bill summary to load.
5. Note every line item, the item total, delivery fee, handling fee, small cart fee,
   any other fee, and the grand total.
6. Stop on the cart page. Do not click Proceed to Pay, Place Order or any payment button.

If a product is out of stock or no exact match exists, skip it and list it under "missing".
If a login page appears, stop and return { "error": "logged_out" }.
If an access denied page or CAPTCHA appears, stop and return { "error": "blocked" }.
```

## Approval and safety rules

- Jhola never clicks a payment, place-order or checkout-confirm button. Every goal says so, and the user pays in the app themselves.
- Nothing goes into a cart until the user taps Approve on the plan.
- Substitutes need the user's approval on the plan page.
- If the cart total an agent reads differs from the planned total by more than Rs 10, Jhola shows the difference and asks again.
- Clearing an existing cart is shown to the user before the fill run starts.

## Failure handling

| Failure | What Jhola does |
| --- | --- |
| Run returns `logged_out` | Marks that app's login as expired and links the user to setup for that app |
| Run returns `blocked` or `SITE_BLOCKED` | Retries once through the Browser scan, then plans without that app |
| Item not found on an app | The optimiser treats that item as unavailable on that app |
| Item not found anywhere | Listed as "not available" on the plan page |
| `COMPLETED` with empty or invalid result | Treated as a failure. Jhola checks every result against the schema. |
| Stream drops | Backend polls `GET /v1/runs/{id}` until the run finishes |
| Planned and actual cart totals differ | Shown to the user before payment |

## Data shapes

```ts
type App = "blinkit" | "zepto" | "instamart";

type ListItem = { id: string; name: string; quantity: number; unit: "g" | "ml" | "pc";
  brand?: string; allowSubstitute: boolean };

type Offer = { app: App; itemId: string; productName: string; packSize: number;
  packUnit: "g" | "ml" | "pc"; price: number; mrp?: number; inStock: boolean;
  matchKind: "exact" | "size_variant" | "substitute" };

type FeeRules = { app: App; deliveryFee: number; handlingFee: number;
  smallCartFee: number; smallCartThreshold: number; otherFees: number };

type Plan = { apps: App[]; lines: { itemId: string; offer: Offer; packs: number }[];
  feesByApp: Record<App, number>; total: number; bestSingleAppTotal: number };
```

## Not in today's build

- Automatic payment. The user pays.
- More apps such as BigBasket or Flipkart Minutes.
- Bank card offers and coupons.
- A separate login for each Jhola user. Today there is one household with one set of profiles.
- Quality scoring beyond the Rs 5 tie-breaker on app rating.
